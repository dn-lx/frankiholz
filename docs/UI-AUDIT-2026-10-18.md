# Public homepage and Admin UI audit — 18 October 2026

Scope: the public homepage, booking/payment step, and all five Admin sections on develop. No production main release, booking cancellation, refund or new charge was performed.

| Finding | Change | Verification |
| --- | --- | --- |
| Received order was unclear because the visible date was a charge schedule | Show immutable received time in Europe/Berlin, newest first, with a deterministic ID tie-breaker; add request refresh | Shuffled records and unrelated payment updates preserve received order; first-load error can recover |
| Long messages and contact details escaped booking cards | Wrap unbroken text, preserve message line breaks, separate identity, receipt time, badges, stay, contact and actions | Long-content Admin checks at 360, 768 and 1280 pixels |
| Missing-photo covers were taller than room photos and actions sat at different heights | Match cover heights and use a flex card body to align price/action footers | Mixed photo/placeholder cards with varied descriptions keep matching cover and button geometry |
| Grid tracks could grow with content | Use shrinkable grid tracks and children in booking and form layouts | Homepage and booking form in English/German at the same widths |
| Hidden Stripe environment input extended beyond its panel | Bound the invisible input to one pixel inside its label | All five Admin tabs have no horizontal document overflow at audited widths |
| Form labels were visually adjacent but not associated | Associate 44 static/rendered labels with controls plus generated bilingual CMS labels | Required public booking controls have accessible labels |
| Integration description referred to old authorization/capture behavior | Explain saving a method and the current 14-day charge schedule | Independent payment review; no change to mode-switch confirmation/security |
| New bank transfers were no longer wanted | Remove the new-transfer offer and reject it in LIVE/TEST setup endpoints | Mocked endpoint checks deny new transfers, retain saved methods and reuse existing instructions |

Existing transfer records keep instructions, receipt webhooks, reconciliation and refund support. SEPA Direct Debit and the other eligible Stripe-hosted methods remain available. Existing financial records are preserved.

Validation: full local Chromium suite (68 checks), followed by the matching-cover/action regression, 15 mocked financial-state checks, syntax and diff checks, and independent payment/guest-data review. Required Chromium/WebKit and security CI runs protect the develop merge. Automated browser fixtures make no real reservations, transfers or charges.
